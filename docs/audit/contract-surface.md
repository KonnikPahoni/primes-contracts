## Methodology

- **Responsibility**: one line, transcribed from the contract file's own header comment.
- **Lines**: raw line count. **Non-comment**: lines that are non-blank and do not start
  with `//`, `*` or `/*` — which excludes the large header doc-comment blocks.
- **Opcodes handled**: arms of the `match (msg)` union dispatch in `onInternalMessage`.
  Tolk dispatches on the message struct, so each arm is one 32-bit opcode, taken from
  the arm struct's `struct (0x…)` declaration.
- **Get-methods**: `get fun` declarations, TEP-62/TEP-74 aliases included.
- **Bounce**: `onBouncedMessage` shape — how many opcode-guarded arms it has, or
  `unguarded rollback` (one message type, restored unconditionally), or `present, no-op`.
- **Outbound**: message structs the contract declares and constructs but does not handle.
  A message whose struct is declared in the *receiving* contract is counted on the
  receiver's inbound side only; `wire-format.md` is the cross-contract view.
- **Storage fields**: top-level fields of `struct Storage`. Several contracts push
  sub-structs into ref cells (Tolk's ~1023-bit / 4-ref limit), so this counts the root
  cell's fields, not the transitive field count.
